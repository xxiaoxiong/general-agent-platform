# AI-GeneralPlat：智能体对话语音输入功能实施任务书

## 1. 目标

在项目现有的**智能体对话页面**中增加语音输入能力，交互体验对齐 ChatGPT
网页版的语音听写（Dictation）：

1.  用户点击输入框旁的麦克风按钮。
2.  浏览器开始录音，并显示录音状态。
3.  用户结束录音后，音频上传到本地 ASR 服务。
4.  ASR 将语音转换为文字，结果填入当前对话输入框。
5.  用户可以检查、编辑文字，再按原有发送按钮提交给 Agent。

**本次只实现"语音转文字并填入输入框"，不实现实时语音通话。**
不做语音回答、TTS、连续语音对话或边说边实时出字。

## 2. 技术方案

-   **ASR 框架：** FunASR
-   **模型：** SenseVoice-Small
-   **部署方式：** Docker Compose，CPU 推理
-   **运行环境：** 开发机 Docker Desktop
-   **调用方式：** HTTP 文件转录 API
-   **前端录音：** 浏览器 `MediaRecorder`
-   **后端调用：** 由项目后端代理调用 ASR，不让浏览器直接访问 ASR 容器

优先使用 FunASR 官方 `examples/openai_api` HTTP
服务及其当前支持的转录接口：

`POST /v1/audio/transcriptions`

模型、参数、启动命令和接口字段以实施时的 FunASR
官方仓库及示例为准，不要照搬过期教程或未经验证的镜像。

官方资料： - https://github.com/modelscope/FunASR -
https://github.com/modelscope/FunASR/tree/main/examples/openai_api -
https://modelscope.cn/models/iic/SenseVoiceSmall

## 3. 实施范围

### 3.1 先检查现有项目

开发前先检查当前仓库，确认：

-   智能体对话页面及输入框组件的位置。
-   输入框文本状态、附件处理和原有消息发送链路。
-   后端路由、文件上传、鉴权和配置管理方式。
-   当前 Docker Compose 结构及网络配置。

在现有架构内做最小改造，不重构聊天模块，不改变 Agent Runtime
和原有消息协议。

### 3.2 Docker 部署 ASR 服务

在项目合适位置增加独立的 ASR Docker 部署配置，建议放在 `deploy/asr/`。

要求：

-   使用 FunASR 官方 HTTP API 示例作为部署基线。
-   使用 SenseVoice-Small，明确配置 CPU 推理，不依赖 GPU/CUDA。
-   使用 Docker Compose，适配开发机 Docker Desktop。
-   模型首次启动时下载，后续通过持久化 Volume
    缓存，避免每次重建容器重新下载。
-   配置容器重启策略及健康检查。
-   ASR 仅供本机或项目内部网络访问，不直接暴露公网。
-   提供简洁的启动、停止、查看日志和健康检查说明。
-   不要把 ASR 模型加载到项目后端进程中。

### 3.3 后端集成

在现有后端增加语音转录接口，例如：

`POST /api/asr/transcribe`

具体路由位置和返回格式遵循项目现有规范。

后端负责：

-   接收前端上传的录音文件。
-   校验文件大小、格式和录音时长。
-   调用 Docker 中的 FunASR HTTP 转录接口。
-   将识别文本以项目统一响应格式返回前端。
-   处理 ASR 不可用、超时、空识别结果和无效音频等异常。
-   复用现有鉴权和日志机制。
-   不长期保存原始录音，不在日志中记录音频内容或不必要的敏感转录内容。

ASR
地址、模型名、超时、文件大小限制等通过环境变量或项目配置管理，不得硬编码。

### 3.4 智能体对话前端集成

只在**现有智能体对话输入框**增加麦克风入口，不另建独立语音页面。

交互要求：

-   点击麦克风开始录音，再次操作或点击停止按钮结束录音。
-   清晰展示录音中、识别中、识别完成等状态。
-   支持取消录音。
-   录音结束后上传音频并等待识别结果。
-   识别完成后将文字填入当前输入框。
-   保留用户原有输入内容，不得无提示覆盖。
-   用户可以修改识别结果。
-   **不得自动发送消息**，必须由用户点击原有发送按钮。
-   识别失败时给出明确提示，并允许重新录音。
-   录音结束、取消、组件卸载或页面离开时，停止麦克风轨道并释放资源。

使用 `MediaRecorder`，根据浏览器支持情况选择音频 MIME
类型；不要假定所有浏览器都输出相同格式。上传文件的 MIME
类型和文件名扩展名应与实际录音格式一致，并验证后端解码兼容性。生产环境需要
HTTPS；本机 localhost 开发按浏览器安全上下文规则处理。

## 4. 明确不做的内容

本次不实现：

-   WebSocket 流式识别。
-   边说边实时显示转录文字。
-   ChatGPT Voice Mode 式实时语音对话。
-   AI 语音回答或 TTS。
-   GPU 推理。
-   Redis、Celery 或分布式任务队列。
-   Agent Runtime 改造。

后续确有实时交互需求时，再单独规划 WebSocket 版本。

## 5. 验收标准

必须完成真实端到端验证：

1.  Docker Desktop 中 ASR 容器可以构建、启动并正常加载模型。
2.  使用一段真实音频调用 ASR HTTP API，能够返回正确结构的转录结果。
3.  在智能体对话页面可以授权麦克风、录音、停止和取消。
4.  录音上传后，识别文字能正确填入当前输入框。
5.  用户可以编辑识别文字，再通过原有发送按钮发送。
6.  Agent 收到的消息与用户手动输入文本走完全相同的原有链路。
7.  ASR
    服务停止、网络异常、权限拒绝、无效音频和超时等情况有明确提示，不影响普通文本对话。
8.  容器重启后模型缓存仍然有效。
9.  不保存不必要的原始录音，不向公网暴露 ASR 服务。

完成后提供简要交付说明：修改文件、Docker
启停方式、配置项、实际测试结果及已知限制。未实际执行的测试必须明确标注，不得声称通过。
