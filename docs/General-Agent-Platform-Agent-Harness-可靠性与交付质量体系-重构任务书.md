# General Agent Platform --- Agent Harness 可靠性与交付质量体系深度重构任务书

> 交付对象：Codex / Trae\
> 项目：`xxiaoxiong/general-agent-platform`\
> 任务类型：现有架构增强与关键链路重构\
> 审查基线：`2405c89a3a41e0bf7228fb05bd2dafdcfae98ac5`（实施前必须重新检查最新
> `main`，以实际代码为准）

## 1. 改造目标

本次改造不是增加更多 Agent、工具或工作流，也不是推倒重写现有 Runtime。

目标是在现有 DeepAgents、LangGraph、Agent Team、Work Orchestrator 和
Project Verifier 基础上，形成统一的 Harness 质量保障体系，使平台能够：

1.  正确理解并持续跟踪复杂任务目标。
2.  在长时间执行、上下文压缩和 Worker 恢复后保持任务连续性。
3.  对研究结论、代码、文档及其他交付物进行可验证的质量检查。
4.  发现交付缺口后有边界地修复、复验。
5.  只有满足验收条件时才允许报告任务完成。
6.  用可复现的真实任务评测证明改造是否有效。

核心原则：**执行完成不等于任务完成；产物存在不等于产物正确；引用存在不等于结论得到来源支持。**

## 2. 改造范围与约束

### 2.1 涉及范围

-   Agent Runtime / Goal 生命周期与执行预算
-   Completion / Task Contract / Verification
-   Work Orchestrator
-   Agent Team Runtime
-   Project Verifier 与代码交付验收
-   Context、Memory、Checkpoint 与恢复流程
-   Evaluation、Judge、Verifier 和长程评测数据集
-   运行轨迹、证据记录、成本与质量指标

### 2.2 保留现有能力

优先复用现有 DeepAgents 主执行引擎、原生 Tool Calling、LangGraph
StateGraph / Checkpointer、Run Worker / Lease / Fencing / Tool Execution
Ledger、Task Board / Member Runtime / Artifact Store、Project
Verifier、Evaluation Runner。

不要另起一套平行 Runtime，也不要为了统一协议一次性替换所有执行器。

### 2.3 实施约束

-   不引入分布式架构作为本次前提，沿用现有部署模式。
-   不把 LLM Judge 作为唯一验收依据。
-   不通过增加模型调用次数掩盖验证机制缺失。
-   不允许将 `partial`、`unverified` 或验收异常当成成功。
-   对外部副作用保持现有幂等和人工核对保护。
-   新机制支持配置开关、灰度启用和回滚。
-   不破坏现有 API、事件协议、会话数据和历史 Run 读取兼容性。

## 3. P0：统一 Verification 协议，修复错误完成风险

这是第一优先级，必须先完成。

### 3.1 建立统一验证数据模型

新增或整理统一的 `VerificationResult`、`VerificationCheck`
等结构，至少包含：

-   `status`：`passed / partial / failed / unverified`
-   `checks`：逐项验收结果
-   `severity`：`blocking / warning / info`
-   `evidence_refs`：工具记录、文件、测试报告、来源等证据引用
-   `missing_items`：未满足的验收项
-   `repairable`：是否可以自动修复
-   `stop_reason`：停止或无法验证的原因
-   `verifier_version`：验证规则版本

任务执行状态与验证状态必须分离。`running / completed / failed / cancelled`
等执行状态不能代替质量验收状态。

### 3.2 统一状态语义

-   `passed`：所有阻塞性验收项通过，证据充分。
-   `partial`：有可用成果，但至少一项必要验收尚未通过。
-   `failed`：关键验收失败，或没有可用交付。
-   `unverified`：缺少足够证据，无法判断是否正确。

最终 Run / WorkPlan / Team 只有在所有必要验收项通过时才能进入成功状态。

特别注意：

-   `partial` 不得映射为步骤 `completed`。
-   `unverified` 不得映射为 `passed`。
-   Verifier 异常、超时或预算耗尽不能默认通过。
-   可交付部分成果时，应保留产物并明确披露未通过项，但不能伪装成完整成功。

### 3.3 修复已发现的高风险链路

重点复核并修复：

-   `backend/app/services/work_orchestrator/adapters/deep_agent.py`
-   `backend/app/services/work_orchestrator/adapters/base.py`
-   `backend/app/services/work_orchestrator/verification.py`
-   `backend/app/services/assistant/verification.py`
-   `backend/app/services/assistant/task_contract.py`
-   `backend/app/services/agent_runtime/completion.py`
-   `backend/app/services/agent_runtime/service/stream.py`

重点检查 `DeepAgentAdapter` 将 `partial` 映射为 `completed` 的逻辑，以及
Work Orchestrator
最终验收是否只检查步骤完成状态、产物和副作用，而遗漏步骤的阻塞性验证结果。

最终验收必须读取每个步骤的真实
VerificationResult，并按统一规则聚合，不能只看步骤执行状态。

### 3.4 验收测试

至少覆盖：

1.  网络检索成功但引用核验失败，最终不得成功。
2.  产物已生成但关键测试失败，最终不得成功。
3.  Verifier 超时或异常，最终不得成功。
4.  部分步骤成功、部分步骤失败，最终应为部分交付或失败。
5.  所有阻塞项通过、只有非阻塞警告，允许成功并披露警告。
6.  外部副作用结果未知时，不得自动宣称成功或盲目重放。

## 4. P0：建立 Claim-Evidence 事实证据核验机制

目标是从"检查有没有引用"升级为"检查结论是否被证据支持"。

### 4.1 建立统一证据结构

每条重要事实主张应能关联：

-   Claim ID 与主张文本
-   Claim 类型：事实、数据、推断、预测、建议
-   Evidence ID
-   原始 URL / 文件路径 / 工具调用记录
-   来源标题、发布时间或获取时间（可获取时）
-   原文片段及定位信息
-   来源读取状态
-   Evidence 与 Claim
    的关系：`supports / contradicts / partially_supports / unrelated`
-   核验状态与理由

证据必须可追溯到真实工具账本或用户提供的文件，不能只接受模型自行生成的
URL、摘要或引用编号。

### 4.2 核验流程

对研究、分析、竞品调研、技术比较等任务：

1.  从最终报告中识别关键 Claim。
2.  为每条关键 Claim 关联实际读取的来源。
3.  检查来源内容是否直接支持 Claim，而不是只检查 URL 是否存在。
4.  对重要结论检查来源质量、时效性和适用范围。
5.  对存在争议的结论记录反向证据。
6.  区分已证实、部分支持、存在冲突、推断和无法核实。
7.  将证据缺口传给修复流程或最终报告。

不要求所有普通句子都拆成
Claim。优先核验影响决策的事实、关键数字、排名、能力判断、因果结论和明确承诺。

### 4.3 验证器设计

采用"确定性检查 + 语义核验 + 必要时独立复查"的组合：

-   确定性检查：URL、来源读取记录、文件定位、时间戳、数据一致性。
-   语义核验：判断证据是否支持 Claim、是否过度推断。
-   独立复查：对高影响或冲突结论重新读取原始来源，必要时寻找反例。

LLM Judge 只能提供语义判断，不能单独决定事实为真。证据不足时必须允许返回
`unverified`。

### 4.4 兼容现有机制

复用并升级 `assistant/verification.py` 中的引用与 Web Evidence
检查、`ToolEvidence` / Tool Execution Ledger、Team Evidence
Review、Evaluation Judge 与证据输入。

保留现有简单任务的低成本路径，不要让每个普通问答都触发完整 Claim 核验。

### 4.5 验收测试

构造以下反例：

-   URL 真实存在，但正文不支持结论。
-   来源只支持部分结论，模型却写成确定事实。
-   多个来源互相矛盾。
-   引用来自用户提供但本次未读取的 URL。
-   搜索工具成功，但抓取内容失败。
-   来源过时，结论却被描述为当前状态。
-   报告含有无来源支持的关键数字。

验证器必须能够识别问题并给出可定位的证据缺口。

## 5. P0：建立 Goal Supervisor，解决长程任务监督问题

不要继续依靠无限循环和超大递归上限维持长任务。

### 5.1 设计目标

在 Agent Loop 外建立持久化的 Goal Supervisor，负责：

-   维护用户原始目标和硬约束。
-   维护验收标准及其状态。
-   跟踪已完成、进行中、阻塞和待验证事项。
-   判断当前执行是否产生有效进展。
-   判断是否需要重新规划、修复、等待或停止。
-   管理全局预算和任务截止条件。
-   在 Worker 接管或上下文压缩后恢复任务状态。

Supervisor 管理任务生命周期，不替代 DeepAgents 内部推理和工具执行。

### 5.2 持久化 Goal State

至少保存：

-   `goal_id`、原始目标、目标版本
-   任务约束和验收标准
-   当前计划与步骤依赖
-   各步骤执行状态和 VerificationResult 引用
-   已验证事实、关键决策及其证据
-   已尝试方案、失败原因和禁止重复事项
-   当前阻塞项、下一步行动
-   当前预算消耗、剩余预算
-   最近进展时间和停滞原因
-   Checkpoint / Artifact / Event 引用

关键状态必须持久化，不能只存在模型上下文或临时内存中。

### 5.3 有边界的执行与续跑

将长任务改为可持续续跑的执行切片：

1.  Supervisor 读取 Goal State。
2.  选择当前最有价值的下一步。
3.  Agent 执行一个有预算边界的阶段。
4.  保存状态、证据和产物。
5.  评估进展与验收缺口。
6.  需要时触发修复或重新规划。
7.  预算不足时暂停并保留可恢复状态。
8.  满足验收条件后才结束。

增加全局预算：模型调用次数、输入 Token、输出
Token、工具调用次数、执行时间、重试次数和成本。Goal 模式不能因为
`goal_mode` 就绕过预算。

### 5.4 停滞检测

至少识别：

-   相同问题反复尝试。
-   工具调用持续发生但验收状态没有变化。
-   计划反复改写但没有产物进展。
-   相同错误持续出现。
-   预算消耗过快。
-   任务长期没有有效进展。

停滞时采取有限重试、改变策略、请求用户补充信息或暂停，不允许无限循环。

### 5.5 验收测试

-   长任务运行中 Worker 被终止，接管后继续正确推进。
-   上下文压缩后仍保留目标、约束、关键决策和未完成事项。
-   连续失败不会无限消耗预算。
-   计划调整后历史决策和已验证证据仍可追溯。
-   预算耗尽时能暂停并恢复，而不是伪装完成。
-   用户取消后能够安全停止并保留已有成果。

## 6. P1：建设 Long-term Working Context

目标是解决"Checkpoint 恢复了执行状态，但模型没有恢复任务认知"的问题。

### 6.1 结构化上下文

将长任务上下文拆分为：

1.  Goal：原始目标与不可变约束。
2.  Plan：当前计划、依赖与验收项。
3.  Verified Facts：已核验事实及证据引用。
4.  Decisions：关键决策、原因和被否决方案。
5.  Progress：已完成工作和未完成工作。
6.  Failures：失败尝试、原因及避免重复的提示。
7.  Next Actions：下一步行动及优先级。
8.  Artifacts：产物路径、版本和校验信息。

### 6.2 压缩策略

-   不允许只用一段自由文本总结全部历史。
-   原始目标、硬约束、未通过验收项、关键事实和证据引用必须保留。
-   历史过程可以压缩，但要保留可回溯引用。
-   压缩前后记录版本和摘要差异。
-   恢复时先加载结构化 Working Context，再按需检索历史细节。
-   对旧 Checkpoint 和旧会话保持兼容。

优先复用 DeepAgents / LangGraph
已有上下文机制，在其外部补齐平台级结构化状态，不要重复实现一套完整框架。

### 6.3 验收测试

使用包含多轮决策、失败修复、上下文压缩和 Worker
恢复的长任务，检查恢复后是否记住原始目标与约束、不重复已失败方案、不丢失关键事实及来源、不覆盖已通过验收的成果，并能正确选择下一步行动。

## 7. P1：统一交付质量门禁

将不同执行路径的验收能力逐步收敛到统一 Verification
协议，但保留不同类型任务的专用验证器。

### 7.1 按任务类型选择验证器

**代码 / 软件项目**

-   文件和源码完整性
-   依赖安装与构建
-   单元测试、集成测试
-   API 和关键业务行为
-   浏览器端关键流程
-   安全与配置检查
-   需求覆盖与源码证据关联

优先复用现有 Project Verifier，不要重复开发隔离执行环境。

**研究 / 分析**

-   关键 Claim 覆盖
-   来源读取与证据支持关系
-   关键数字和时间有效性
-   多来源交叉核验
-   反面证据和不确定性披露

**长文档**

-   结构和模板符合性
-   必要章节和内容完整性
-   关键事实、数字和引用一致性
-   多轮修改内容保留
-   文件可打开、格式有效
-   用户明确要求的排版规则

**数据 / 数学任务**

-   输入数据来源
-   计算过程可复现
-   结果独立复算
-   单位、边界和异常值检查
-   输出格式及字段准确性

### 7.2 统一交付报告

每个复杂任务形成机器可读的 Delivery Report，至少包括：

-   原始目标和验收标准
-   最终交付物及版本
-   每项验收结果
-   证据引用
-   未解决问题
-   风险与不确定性
-   修复次数
-   实际成本和耗时
-   最终状态及原因

用户界面应清晰区分"已完成""部分交付""未通过""无法核验"，不能只展示模糊的成功标志。

## 8. P1：提升 Team Runtime 的证据协作能力

不以增加成员数量为目标，重点提高协作后的最终正确率。

### 8.1 改进方向

-   成员交付结构化结果，而非只有自由文本。
-   成员共享关键 Claim、Evidence 和 Artifact 引用。
-   Leader 综合时检查事实冲突和重复结论。
-   独立 Reviewer 能定位到原始来源或实际产物。
-   返工必须针对具体失败的验收项。
-   返工后必须重新核验，不得仅凭成员声明通过。
-   成员失败、预算不足和复核未完成必须进入最终披露。

### 8.2 共享边界

保留成员职责隔离和工具权限控制。通过 Task Board、Artifact Store
和结构化证据共享必要上下文，不要把完整历史会话无差别复制给所有成员。

### 8.3 并发与成本

先完善现有并发预算的统计和可观测性。若当前仍采用进程级模型
Semaphore，应明确多 Worker
下的总并发上限并防止误认为是全局限制；暂不以引入 Redis
或分布式调度作为前提。

## 9. P1 / P2：升级 Evaluation，建立真实能力基准

现有 Evaluation Runner、数据集、Judge 和 Verifier
优先保留。重点提高测试真实性和结果可信度。

### 9.1 新增评测场景

至少建立五类端到端任务：

  -------------------------------------------------------------------------------------------
  类型                    任务示例                       核心验收
  ----------------------- ------------------------------ ------------------------------------
  长程软件开发            从需求开发一个中型业务系统     构建、测试、业务行为、需求覆盖

  深度研究                对技术或产业问题进行研究       Claim 支持率、事实错误、来源质量

  长文档                  生成并多轮修改正式报告         事实一致性、内容保留、格式有效

  多 Agent 协作           多模块依赖任务                 最终质量、协作增益、返工率

  故障恢复                执行中断、上下文压缩、Worker   恢复正确性、重复副作用、目标连续性
                          接管                           
  -------------------------------------------------------------------------------------------

每类先建立少量高质量、可复现用例，再逐步扩充。不要用大量关键词匹配用例制造虚假的评测规模。

### 9.2 评测指标

至少统计：

-   Task Success Rate：严格验收通过率
-   Delivery Accuracy：交付正确率
-   Evidence Support Rate：关键 Claim 的证据支持率
-   False Completion Rate：错误宣布完成的比例
-   Recovery Success Rate：中断恢复后继续正确完成的比例
-   Requirement Coverage：需求覆盖率
-   Regression Rate：修复后回归失败率
-   Cost per Successful Task：每个成功任务的实际成本
-   P50 / P95 Duration：任务耗时分布

其中 `False Completion Rate` 必须作为核心质量指标。

### 9.3 评测可信度要求

-   Verifier 尽量使用可确定性复算的标准。
-   LLM Judge 与被测模型尽量解耦，并记录 Judge 模型和 Prompt 版本。
-   Judge 评分失败应标记为 `inconclusive`，不得默认通过。
-   长文档和代码项目不能只截取前几千字就声称完成全面评审。
-   记录完整产物 Hash、工具轨迹、测试报告和评分依据。
-   每个关键任务至少进行 3
    次独立运行，观察稳定性；高成本任务可先小规模试跑。
-   保存基线成绩，改造前后使用相同模型、配置、预算和任务集对比。

## 10. P2：统一资源预算与运行可观测性

将以下资源统一归属到 Run / Goal / Team / Member：

-   输入 Token、输出 Token
-   模型调用次数及耗时
-   工具调用次数及耗时
-   Sandbox / Project Verifier 执行时间
-   重试和返工次数
-   总执行时长
-   实际费用（可获取时）
-   预算上限与剩余预算

重点检查现有 `ExecutionBudget`、`ModelUsageCallback` 和 Team 容量控制：

-   `max_tokens_budget` 是否真正参与预算判定。
-   输入 Token 是否完整累计。
-   多成员、多模型调用是否统一计入父 Run。
-   超预算时是否安全暂停并保留状态。
-   多 Worker 下进程级 Semaphore 是否造成全局并发超限。

不得将估算成本标记为实际费用；无法获取的指标应明确标记缺失。

## 13. 最终交付要求
