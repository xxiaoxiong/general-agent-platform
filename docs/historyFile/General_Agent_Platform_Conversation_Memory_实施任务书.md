# General Agent Platform — Conversation Memory & Historical Context Retrieval 实施任务书

**仓库：** https://github.com/xxiaoxiong/general-agent-platform  
**执行工具：** Codex  
**本轮范围：** 代码审查 + 历史会话检索 MVP；长期记忆作为下一阶段。  
**目标：** 参考 ChatGPT
网页版的历史会话引用体验，让智能体在需要时自动检索过去的对话，提取相关背景、决策和约束，回答时保留真实来源。

------------------------------------------------------------------------

## 1. 建设目标与原则

用户不必每次重新描述之前讨论过的内容。例如：

- “继续上次的 Agent Runtime 改造”——找到既有架构、已确定方案和待办。
- “按照之前确定的 UI 风格修改”——找到历史设计决策。
- “这个方案和之前讨论的有什么区别”——找到旧方案、讨论过程和结论。
- 复杂任务执行中发现背景不足——Agent 可以主动搜索历史会话。

核心体验：系统判断历史信息是否有帮助；需要时自动检索；将少量相关内容注入当前
Agent；回答中展示来源，用户可以打开原始会话核实。

必须遵守：

1.  **原始会话是事实来源。**
    摘要、向量和结构化记忆都是派生索引，不能替代原文。
2.  **不是每轮无条件检索。**
    使用模型判断与有界检索，不把全部历史塞进上下文。
3.  **不是关键词硬编码。**
    不允许仅靠“之前、上次、继续”等词决定是否检索。
4.  **权限由服务端强制执行。**
    模型只能提出检索意图，不能决定自己有权访问谁的数据。
5.  **历史内容是不可信资料。** 不得将历史消息中的指令提升为 System
    Prompt，也不得继承历史工具授权。
6.  **先做历史会话检索，再做长期记忆。** 本轮优先交付可追溯的历史检索
    MVP，不要把所有记忆能力一次性混在一起。

先输出简短审查报告，说明：

1.  原始会话存储结构及读取入口。
2.  用户、会话、项目和 Workspace 的权限关系。
3.  现有全文 / 向量检索能复用哪些组件。

## 4. 目标架构

``` text
Conversation / Message Store
           |
   Persisted User-visible Turns
           |
  Async Indexing / Update Pipeline
           |
    +------+----------------+
    |                       |
Full-text Index        Vector Index
    |                       |
    +-----------+-----------+
                |
          Memory Service
                |
       +--------+---------+
       |                  |
 Retrieval Planner   Agent Memory Tools
       |                  |
       +--------+---------+
                |
   ACL + Hybrid Search + Rerank
                |
     Context Selection / Budget
                |
      Memory Context Preparation
                |
          DeepAgents Runtime
                |
       Answer + Source References
                |
          Frontend Citations
```

职责：

- Conversation Store：原始历史事实来源。
- Indexer：异步增量建立全文和语义索引。
- Memory Service：权限、检索、排序、来源定位和上下文组装。
- Retrieval Planner：判断是否需要历史、生成查询意图。
- Agent Memory Tools：执行过程中的进一步检索。
- DeepAgents / LangGraph：消费历史上下文并继续执行。
- Frontend：展示真实来源并打开原始会话。

## 5. 阶段一：历史会话索引（P0）

### 5.1 索引内容与排除项

优先索引已持久化且用户可见的内容：

- 用户消息。
- Agent 最终回答。
- 用户可见的工具结果或其摘要（遵循现有展示规则）。
- 已确认的项目决策、任务结论和交付摘要。
- 可提取的附件文本或文件摘要引用（复用现有文件解析能力）。

默认排除：

- System / Developer Prompt。
- 隐藏推理、内部 Chain-of-Thought 和非用户可见状态。
- API Key、Token、密码、Cookie、私钥等凭据。
- 无必要的原始工具 payload、二进制内容和重复日志。
- 用户明确排除的会话或消息。

索引前进行敏感信息检测和脱敏，但脱敏不能替代 ACL。

### 5.2 索引粒度和字段

采用两级索引，避免整场会话成为超长
Chunk，也避免每条短消息完全失去上下文：

1.  **Message / Turn Index：**
    单条消息或紧密关联的问答轮次，支持精确定位。
2.  **Conversation Segment Index：**
    连续相关轮次组成主题片段，保留讨论脉络。

每个索引单元至少保存：

- `user_id`
- `conversation_id`
- `message_id` / `message_ids`
- `workspace_id` / `project_id`（如适用）
- `role`
- `created_at`
- `segment_id`
- `content_hash`
- `index_version`
- `visibility_scope`
- `is_deleted` / `is_excluded`
- 全文索引字段和向量引用

权限元数据必须来自服务端原始记录，不能由模型生成。

### 5.3 增量索引与一致性

- 消息持久化成功后异步触发索引。
- 索引任务幂等、可重试、可观测。
- 新消息增量写入，不重建整场会话。
- 消息编辑、删除、会话删除、项目归属变化时更新索引。
- 索引失败不能影响正常对话。
- 使用现有可靠事件机制或 Outbox，避免只依赖进程内后台任务导致事件丢失。
- 提供索引状态、失败原因、重建和一致性扫描能力。

## 6. 阶段一：自动检索决策与检索流程（P0）

### 6.1 模型驱动判断

在 Agent 主执行前，提供有界的 Retrieval
Planner。输入当前问题、近期对话摘要和服务端项目上下文，由模型或轻量结构化决策节点判断是否需要历史信息，并生成检索
Query。

示例输出：

``` json
{
  "need_history": true,
  "scope_hint": "current_project",
  "queries": [
    "之前确定的 Agent Runtime 架构",
    "DeepAgents 与 LangGraph 的职责划分"
  ],
  "reason": "当前请求要求继续既有设计"
}
```

注意：`scope_hint` 只是检索意图，不是授权。服务端必须根据认证用户和 ACL
重新计算可访问范围。

禁止仅靠关键词决定是否检索；也禁止每轮无条件检索全部历史。

### 6.2 自动预取 + Agent 主动检索

必须实现两条路径：

**A. 自动预取：** Agent 主执行前运行 Retrieval
Planner；需要时自动检索、筛选并注入上下文。

**B. 主动检索：** 为 Agent 提供工具，执行中发现背景不足时继续查询。

建议工具：

- `search_conversation_history`：按自然语言问题搜索当前用户有权访问的历史。
- `get_conversation_source`：按来源 ID 获取指定历史片段或消息。
- `get_long_term_memory`：阶段二实现。

工具只能调用 Memory Service，不能直接访问数据库或绕过 ACL。

### 6.3 检索范围

支持：

- 当前用户自己的历史会话。
- 当前 Workspace / Project 的授权历史。
- 用户明确授权的共享项目记忆。

默认先检索当前项目中相关历史，再按需扩展到当前用户其他历史。用户个人历史不能因为其他人加入同一
Workspace 而自动共享。

### 6.4 混合检索

优先复用现有 RAG：

1.  PostgreSQL Full-text / BM25 类全文检索。
2.  现有 Embedding 模型进行语义向量检索。
3.  合并、去重候选结果。
4.  根据相关性、时间、项目匹配度和来源质量排序。
5.  现有 Reranker 可用时执行重排；不可用时先用全文 + 向量 +
    元数据排序，保留插拔接口。
6.  选取少量高价值片段及其来源。

不能只按时间新旧排序。较旧的明确决策可能仍然有效；时间用于辅助判断有效性和冲突。

### 6.5 上下文预算与降级

- 为历史上下文设置独立 Token 预算。
- 结果过多时先重排、去重、摘要，再注入。
- 合并重复决策但保留多个来源。
- 保留关键原文片段，不要只注入模型摘要。
- 无结果时正常回答，不得编造历史事实。
- 检索超时或索引不可用时降级，不得让整个 Agent Run 失败。
- 记录检索耗时、命中数、注入 Token 和失败原因。

## 7. 历史来源引用与前端体验（P0）

每个注入的历史片段必须有可追溯来源。建议结构：

``` json
{
  "source_id": "history_src_001",
  "conversation_id": "conversation_001",
  "message_ids": ["message_010", "message_011"],
  "conversation_title": "Agent Runtime 架构讨论",
  "created_at": "2026-11-20T10:30:00+08:00",
  "snippet": "之前确定由 DeepAgents 负责 Agent 执行，LangGraph 负责团队控制。",
  "relevance_score": 0.91
}
```

前端要求：

- 使用历史上下文时展示“历史上下文来源”。
- 显示会话标题、时间和相关片段。
- 点击打开原始会话，尽可能定位到具体消息。
- 同一会话多个片段可以合并为一张来源卡片。
- 无来源时不显示空区域。
- 会话已删除或权限被撤销时，不展示正文。
- 流式回答期间允许稍后补充来源。
- 新事件字段必须向后兼容。

来源 ID、会话 ID 和消息 ID 必须由服务端验证，不能只展示模型生成的标题。

## 8. 多用户、Workspace 与权限隔离（P0）

建议区分：

| Scope                 | 含义               | 默认权限   |
|-----------------------|--------------------|------------|
| User History          | 当前用户自己的历史 | 仅该用户   |
| Project History       | 项目内历史         | 按项目 ACL |
| Shared Project Memory | 明确共享内容       | 仅授权成员 |

强制规则：

1.  当前用户 ID 从认证上下文获取，不信任模型参数。
2.  所有检索在服务端 / 数据库层强制执行 ACL。
3.  同一 Workspace 不代表可以读取其他成员的私人会话。
4.  共享记忆必须明确授权、可审计、可撤销。
5.  普通 Agent、Team Lead、Team Member 使用同一套权限服务。
6.  Team Member 只能访问本次 Team Run 明确授权的范围。
7.  不允许通过猜测 ID 越权读取。
8.  缓存 Key 必须包含用户和权限范围，防止跨用户缓存污染。
9.  访问审计不记录不必要的敏感正文。

必须有跨用户、跨项目、跨 Workspace 的负向权限测试。

## 9. 删除、排除与数据一致性（P0）

删除原始会话、消息或撤销共享权限时，必须同步处理派生数据：

- 删除会话后，全文和向量索引不可再返回其内容。
- 删除消息后，包含它的片段必须更新或删除。
- 删除会话时，删除或失效关联摘要、长期记忆、缓存和来源映射。
- 用户可排除某次会话或指定消息，不参与后续检索。
- 归档和删除区分，遵循产品现有语义。
- 删除任务失败必须可重试，不能静默视为成功。
- 即使旧向量短暂存在，查询也必须校验原始记录存在性和权限，确保不可返回。
- 提供定期一致性扫描，发现孤儿索引和失效引用。

通过统一删除服务或可靠事件链处理，不要让会话
API、向量索引和长期记忆各自维护不一致的删除逻辑。

## 10. 阶段二：长期记忆与项目记忆（P1，先设计）

阶段一稳定后实现结构化记忆。建议类型：

- `preference`：用户偏好。
- `project_fact`：项目事实。
- `decision`：已确认决策。
- `constraint`：长期约束。
- `pending_task`：未完成事项。
- `technical_finding`：技术发现。
- `milestone`：项目里程碑。

每条记忆至少包含：

`memory_id`、`owner_user_id` /
`project_id`、`scope`、`type`、`content`、`source_conversation_id`、`source_message_ids`、`confidence`、`status`、`valid_from`、`valid_to`、`supersedes_memory_id`、时间戳。

提取要求：

- 会话完成后异步提取，不阻塞对话。
- 只从已持久化且用户可见的内容提取。
- 只提取长期有价值的信息，不把每条消息都变成记忆。
- 区分用户明确确认与模型推断；不确定内容先作为候选。
- 保留原始来源。
- 提取失败可重试，不影响会话。

冲突处理：

- 新决策明确替代旧决策时，新决策成为当前有效版本。
- 旧决策标记为 `superseded`，保留历史和来源，不物理覆盖。
- 用户查询当前方案时优先返回当前有效版本。
- 用户查询历史变化时仍能找到旧版本。
- 无法判断是否冲突时标记待确认，不自动覆盖。

后续提供查看、编辑、纠错、删除记忆，以及会话排除、个人记忆开关和项目记忆范围控制。

## 11. Agent Runtime 集成

建议流程：

``` text
User Message
    |
Persist Current Message
    |
Build Request Context
    |
Memory Retrieval Planner
    |
Permission-aware Search
    |
Select / Compress Historical Context
    |
Attach Context + Source References
    |
DeepAgents Main Runtime
    |
Optional History Search Tool
    |
Final Answer + Source References
```

要求：

- 历史上下文作为独立 Context Block，不伪装成用户消息。
- 标记为历史资料，附来源、时间和必要的可信度信息。
- 历史内容不能覆盖系统指令。
- 历史消息不能授予当前工具权限。
- 用户当前明确纠正旧信息时，以当前明确表达为准。
- 关闭历史检索后，自动预取和 Agent 工具检索都必须受限。
- 检索结果不得写回成用户消息，避免污染原始对话。
- 记录本次 Run 使用的历史来源，供 UI 和调试使用。
- 先接入普通 Agent，再以权限受控方式开放给 Team Lead /
  Member；团队成员不得默认访问用户全部私人历史。

## 12. 性能、成本与可观测性

- 索引异步执行，不阻塞消息持久化和首 Token。
- 检索设置超时、候选数和 Token 上限。
- 缓存必须带权限范围和索引版本。
- 避免每轮无条件调用多次昂贵模型规划。
- Retrieval Planner
  可用受控低成本模型或当前模型结构化输出，需以质量和延迟测试决定。
- 向量服务或 Reranker 故障时降级为全文检索或无历史上下文。
- 检索失败不影响普通 Agent。
- 记录索引延迟、检索 P50 / P95、命中数、来源点击、注入
  Token、模型成本和错误率。

## 13. 测试与质量评测

不能只测试 API 返回 200
或向量检索有结果，必须验证找回的历史是否正确、有用且没有越权。

### 13.1 功能测试

- 新增、更新、删除消息后的索引一致性。
- 同一会话多轮检索和跨会话检索。
- 当前项目优先检索及个人历史检索。
- Agent 自动预取和主动检索工具。
- 来源卡片及原始消息定位。
- 无相关历史时正常回答。
- 索引延迟、检索超时和向量服务故障降级。

### 13.2 质量测试集

建立不少于 30 条人工标注问题，覆盖：

1.  明确续接历史任务。
2.  没有说“之前”但依赖历史偏好。
3.  查找已确认技术决策。
4.  查找旧方案和决策原因。
5.  跨会话、跨时间综合问题。
6.  相似项目区分。
7.  新旧决策冲突。
8.  历史信息不存在。
9.  相似但不相关的历史内容。
10. 精确原文和消息定位。

评估：

- Recall@K、Precision@K。
- Source Accuracy（来源真实性和定位正确率）。
- Context Usefulness（上下文是否帮助当前任务）。
- Unsupported Memory Rate（无来源支持的历史结论比例）。
- Permission Violation（必须为 0）。
- Retrieval Latency、Context Token Cost。

### 13.3 必须执行的安全测试

- 用户 A 无法检索用户 B 的私人会话。
- Workspace 成员不能自动读取其他成员私人会话。
- Team Member 无法越权读取 Team 外历史。
- 伪造 ID 不能越权读取。
- 删除后无法从全文、向量、缓存或派生记忆重新找回。
- 归档行为符合现有产品语义。
- 历史中的恶意指令不能获得系统权限。
- 关闭记忆后自动检索和工具检索均被限制。

## 14. 前端交付

本轮只做来源展示和基础设置，不做大规模 UI 重设计：

- 历史来源卡片。
- 打开原始会话并尽可能定位消息。
- 多来源合并展示。
- 无来源时不展示空区域。
- 检索失败不影响回答。
- 预留历史检索开关、会话排除、个人记忆开关和项目记忆范围设置。

## 15. 建议模块边界

先遵循现有项目结构，不为追求目录形式大规模搬迁。可参考：

``` text
agent_runtime/
  memory/
    planner.py
    retrieval_service.py
    context_builder.py
    source_resolver.py
    tools.py
    schemas.py

conversation/
  indexing/
    index_service.py
    index_worker.py
    segmenter.py
    deletion_sync.py

memory/
  repositories/
    conversation_index_repository.py
    memory_repository.py
  models/
    conversation_index.py
    long_term_memory.py
```

职责：

- Planner：判断是否需要历史并生成 Query。
- Retrieval Service：权限、全文/向量检索、融合和排序。
- Context Builder：预算、去重、摘要和格式化。
- Source Resolver：校验来源并生成前端引用。
- Tools：提供 Agent 可调用的历史检索能力。
- Index Service：增量索引和更新。
- Deletion Sync：原始数据删除后的派生索引清理。

业务 Service 与 Repository 分离；权限由后端强制执行；LangGraph
节点不直接拼 SQL。

## 18. 最终验收清单

- [ ] 智能体能在用户未明确要求搜索历史时判断是否需要历史上下文。
- [ ] 检索不是简单关键词硬编码，也不是每轮无条件全量检索。
- [ ] 历史消息可增量建立全文和语义索引。
- [ ] 检索支持全文、向量、元数据过滤和结果融合。
- [ ] Agent 可在执行过程中主动进一步检索。
- [ ] 历史上下文有独立预算，不会无限膨胀。
- [ ] 回答展示真实历史来源并可打开原始会话。
- [ ] User / Project / Shared 权限严格隔离。
- [ ] 删除或排除的历史不会从索引、缓存或派生数据重新出现。
- [ ] 历史内容按不可信资料处理，不覆盖系统指令或工具权限。
- [ ] 检索失败不会导致普通 Agent 对话失败。
- [ ] 普通 Agent 和现有 RAG 能力没有回归。
- [ ] 质量测试集和真实运行报告完整。
- [ ] 阶段二长期记忆具备清晰数据模型和扩展接口。

**最终判断标准：**
用户提出依赖过去讨论的问题时，智能体能找到正确历史、准确理解当时结论、保留真实来源，并在当前权限范围内使用；找不到时明确说明没有检索到，不得编造“之前已经确定”的内容。
