> **项目：** General Agent Platform\
> **仓库：** https://github.com/xxiaoxiong/general-agent-platform\
> **执行工具：** Codex\

> **设计方向：** Linear × Claude\

## 1. 项目目标

本次任务不是简单调整颜色、圆角、间距，也不是给现有页面套一层新皮肤，而是将
General Agent Platform 的前端体验升级为成熟商业化 AI SaaS / Agent
Platform 的产品水准。

目标是让平台在视觉一致性、信息架构、交互细节、内容呈现、响应式布局和可维护性方面，尽可能接近
Linear、Claude 等头部产品的成熟度。

### 1.1 目标体验

最终产品应具备以下特征：

1.  **现代、克制、精致：**
    以中性色为基础，减少无意义的装饰、渐变、大面积彩色背景和厚重边框。
2.  **信息层级清晰：**
    用户能够快速识别页面标题、核心内容、主要操作、状态和辅助信息。
3.  **一致的交互语言：**
    导航、按钮、表格、筛选、弹窗、抽屉、空状态、加载状态等使用统一规范。
4.  **AI 原生体验：** Agent
    对话、任务执行、工具调用、审批、文件和结果产物不再像普通聊天组件的简单拼接。
5.  **开发者平台体验：**
    模型、知识库、工作流、运行记录、Trace、评测等功能具有专业、清晰、高效的操作体验。
6.  **长期可维护：** 建立真正可复用的 Design System
    和基础组件，不继续通过页面级 CSS 覆盖堆叠样式。
7.  **渐进式改造：**
    尽量复用已有业务逻辑、API、数据结构和状态管理，避免为了视觉升级而无必要地重写业务。

### 1.2 设计参考及其职责

不要机械复制某个产品的页面，而是吸收各产品最成熟的部分，形成 General
Agent Platform 自己的设计语言。

  --------------------------------------------------------------------------------------------------
  参考产品                            主要借鉴方向
  ----------------------------------- --------------------------------------------------------------
  Linear                              全局布局、侧栏、导航、列表、页面层级、快捷操作、细节与一致性

  Claude                              Agent Workspace、对话体验、任务过程、内容产物、分屏协作

  ChatGPT                             会话历史、消息 Composer、附件、流式生成、对话滚动体验

  Vercel                              开发者平台、项目与资源组织、配置页面、状态、日志和数据表格

  Dify                                Workflow Studio、节点编辑、配置面板、调试与执行结果
  --------------------------------------------------------------------------------------------------

**整体设计以 Linear 为主基准，Agent 工作空间重点借鉴
Claude，其他产品只在对应业务模块中提供参考。**

### 2.2 必须保护的现有能力

本任务的主要目标是前端体验升级，不应擅自改变后端业务契约。

-   Agent 会话、消息、Run、任务状态和流式响应逻辑。
-   工具调用、人工审批、任务中断与恢复等现有能力。
-   模型供应商、模型配置和模型调用链路。
-   知识库、文件上传、文档管理和检索能力。
-   Workflow 的业务数据结构、保存、发布、运行和调试能力。
-   Trace、评测、Agent Evolution 等数据来源和计算逻辑。
-   现有路由、深链接和页面权限控制。

允许为了适配新 UI
对前端组件、页面布局、样式组织和局部状态组织进行重构，但必须确保上述能力不发生回归。

### 2.3 禁止事项

1.  不得为了方便而删除现有页面或功能。
2.  不得使用静态假数据替代真实 API 数据。
3.  不得仅制作一个独立的 UI Demo，却不接入现有业务。
4.  不得将后端业务逻辑迁移到前端。
5.  不得擅自修改 API 契约、数据库结构或业务数据模型。
6.  不得一次性删除 Element
    Plus，除非已完成依赖审计、全量迁移和回归验证。
7.  不得通过全局 `!important` 覆盖的方式掩盖组件冲突。
8.  不得在页面中继续大量堆叠局部硬编码颜色、间距和圆角。
9.  不得为了动画效果牺牲页面响应速度、滚动性能和可访问性。
10. 不得只完成首页或少数展示页面，必须覆盖项目现有的全部主要业务页面。

## 3. 总体视觉设计规范

### 3.1 设计基调

采用 Linear × Claude 的融合方向：

-   页面背景以柔和的浅灰白、中性白为主。
-   内容表面以白色为主，使用非常克制的层级差异。
-   文字以深灰、近黑为主，辅助文字降低对比度。
-   边框使用低对比度中性色。
-   品牌强调色只用于关键操作、选中状态、焦点和少数重要状态。
-   通过留白、字体、层级和布局建立质感，而不是依赖大面积彩色背景。
-   阴影轻量，避免厚重卡片和夸张悬浮效果。
-   不使用无意义的渐变 Banner、装饰性大图标或过度圆润的卡片堆叠。

不要照搬 Linear
的品牌标识、专有图形、产品文案或受版权保护的资产。需要形成平台自己的视觉识别。

### 3.2 Design Tokens

建立集中管理的设计 Token，至少覆盖：

  ------------------------------------------------------------------------------------------------------
  Token 类别                          必须定义的内容
  ----------------------------------- ------------------------------------------------------------------
  Color                               页面背景、表面、浮层、主文字、次级文字、边框、强调色、语义状态色

  Typography                          字体族、字号层级、字重、行高、字间距

  Spacing                             统一间距刻度，优先使用 4px 基准体系

  Radius                              输入框、按钮、卡片、弹窗、浮层等圆角规范

  Shadow                              浮层、弹窗、悬浮元素的轻量阴影

  Border                              默认边框、弱边框、分隔线、焦点边框

  Motion                              过渡时长、缓动曲线、悬停、展开、切换和加载动画

  Z-index                             页面内容、下拉菜单、Popover、Drawer、Dialog 等层级
  ------------------------------------------------------------------------------------------------------

要求：

1.  使用 CSS Variables 管理语义化 Token。
2.  Tailwind 样式必须与 Token 保持一致。
3.  业务组件不得随意定义一套独立颜色体系。
4.  浅色主题作为默认主题。
5.  为暗色主题预留完整的 Token 映射，不能只做简单反色。
6.  语义颜色必须统一，例如成功、警告、错误、运行中、等待中、禁用状态。
7.  字体需要兼容中文与英文，优先采用稳定的系统字体栈；如引入 Web
    Font，评估加载成本和内网部署可用性。

可从以下方向建立初始中性色体系，最终数值由实际页面效果统一校准：

-   页面底色：接近 `#FAFAF9` 的柔和中性色。
-   主表面：`#FFFFFF`。
-   次级表面：接近 `#F5F5F4`。
-   主文字：接近 `#20201F`。
-   次级文字：接近 `#737370`。
-   弱边框：接近 `#E8E8E6`。
-   强调色：选择一套克制的品牌色，并统一应用，不保留现有蓝、绿等多套互相冲突的主色。

上述颜色是设计起点，不是要求逐项照抄。最终必须形成完整、可复用的 Token。

### 3.3 字体与图标

-   建立统一字体栈，兼顾中文、英文、数字和代码。
-   页面标题、正文、辅助信息、表格、代码分别有明确的字号与字重规范。
-   统一使用 Lucide 图标体系（`lucide-vue-next` 或与当前 Vue 生态兼容的
    Lucide 包）。
-   禁止混用 Emoji、Element Plus
    图标和多套风格差异明显的图标作为正式导航图标。
-   图标尺寸、线宽、颜色、对齐方式必须统一。
-   仅在真正具有语义价值的地方使用图标，不要为了装饰而增加图标。

## 4. 前端技术方案与迁移策略

### 4.1 目标技术组合

目标方向：

-   Vue 3 + TypeScript + Vite：继续保留。
-   Tailwind CSS：负责布局、间距、响应式和常用样式。
-   shadcn-vue：作为可复制、可维护的基础组件来源。
-   Reka UI：为 Dialog、Popover、Dropdown、Tooltip、Tabs
    等交互组件提供无样式基础能力。
-   Lucide：统一图标。
-   CSS Variables：管理设计 Token。
-   现有 Element Plus：在迁移期间继续承载尚未替换的复杂业务组件。

shadcn-vue
不是传统的完整组件库。组件代码应由项目自身管理，并根据平台的设计规范进行必要封装和调整。

### 4.2 迁移原则

采用渐进式迁移，不进行一次性推倒重来。

**第一步：** 检查当前
Vue、Vite、TypeScript、构建工具版本，确定与其兼容的 Tailwind
CSS、shadcn-vue、Reka UI 版本及安装方式。

**第二步：** 建立 Token、Tailwind 配置、基础工具函数和基础组件。

**第三步：** 先改造全局 App Shell
和新建的基础组件，再选择核心页面逐步迁移。

**第四步：** 旧 Element Plus
页面逐步替换。对于复杂表格、日期选择、上传等暂时没有必要重写的组件，可以继续使用
Element Plus，但必须统一外观。

**第五步：** 完成全量页面检查后，再决定是否删除不再使用的 Element Plus
依赖。

### 4.3 组件组织建议

根据现有项目实际目录进行调整，不要求机械套用目录结构。建议形成以下职责边界：

``` text
frontend/src/
├── components/
│   ├── ui/                  # shadcn-vue 基础组件
│   ├── common/              # 项目通用业务无关组件
│   ├── layout/              # Sidebar、Header、PageHeader 等
│   ├── data-display/        # 表格、指标、状态展示
│   └── feedback/            # Empty、Loading、Error、Toast
├── layouts/
│   └── MainLayout.vue
├── views/
│   ├── workspace/
│   ├── workflows/
│   ├── knowledge/
│   ├── models/
│   ├── prompts/
│   ├── apps/
│   └── system/
├── styles/
│   ├── tokens.css
│   ├── themes.css
│   └── global.css
└── lib/
    └── utils.ts
```

要求：

-   基础 UI 组件不直接依赖具体业务 API。
-   业务组件不重复实现基础按钮、弹窗、表单等通用能力。
-   避免单个组件承担过多页面职责。
-   样式尽量局部化或通过统一 Token 管理。
-   对 Element Plus 的样式兼容应集中处理，不要在每个页面重复覆盖。
-   不要为了目录整齐而大规模移动与本次任务无关的代码。

## 5. 全局 App Shell 重构

这是所有页面体验的基础，必须优先完成。

### 5.1 左侧导航 Sidebar

参考 Linear 的导航体验：

-   侧栏视觉弱化，不与主内容区争夺注意力。
-   支持展开、收起。
-   支持合理的宽度调整（如果当前布局实现成本可控）。
-   导航分组清晰，避免菜单过长和层级混乱。
-   当前页面、悬停、禁用和展开状态具有统一表现。
-   图标和文字对齐统一。
-   分组标题采用低对比度辅助文字。
-   长导航支持独立滚动。
-   侧栏底部放置用户、设置等稳定入口。
-   不能因折叠状态导致工具提示、点击区域或导航行为异常。

重新审视现有导航信息架构。可以按实际业务将入口组织为：

-   工作空间：智能体对话、应用/Agent 入口。
-   构建与资源：工作流、知识库、提示词、模型、数据库等。
-   运行与评测：运行记录、Trace、Evaluation、Agent Evolution 等。
-   系统管理：用户、审计、系统设置等。

最终分组必须以真实路由和权限为准，不得为了视觉布局创造不存在的功能入口。

### 5.2 顶部 Header

-   保持简洁，避免重复显示过多导航信息。
-   面包屑只在有助于定位时显示。
-   页面级操作放在对应页面的 Header / Toolbar，而不是全部堆在全局顶部。
-   用户菜单、主题切换、全局搜索等入口位置固定。
-   统一高度、边框、对齐和交互状态。

### 5.3 全局命令面板

实现统一的命令面板，目标交互参考 Linear：

-   `Ctrl + K` / `Cmd + K` 打开。
-   支持搜索现有页面和导航入口。
-   支持执行明确存在的常用操作。
-   支持键盘上下选择、Enter 确认、Esc 关闭。
-   有清晰的分组、快捷键提示和空结果状态。
-   不得展示没有真实实现的命令。
-   注意输入框聚焦时避免快捷键冲突。

如果当前阶段无法安全接入全部业务动作，先完成真实可用的全局页面搜索与导航，不要制作假功能。

### 5.4 页面容器与层级

建立统一的页面容器规范：

-   页面标题区。
-   标题与描述。
-   主操作区。
-   Tabs（有需要时）。
-   筛选和工具栏。
-   主内容区。
-   分页或底部辅助信息。

不同页面可以有差异，但相同职责的组件必须有相同视觉和交互规则。

## 6. 核心页面改造要求

必须先通过路由和源码盘点列出当前仓库全部页面，再逐一落实。以下是重点页面的目标要求。

### 6.1 Agent Workspace（最高优先级）

文件入口：`frontend/src/views/workspace/WorkspaceHome.vue`

这是平台最重要的使用入口之一，应重点借鉴 Claude 与 ChatGPT。

#### 布局目标

-   会话历史区。
-   中央对话区。
-   可选的右侧产物 / 上下文面板。
-   底部 Composer。
-   在不同屏幕尺寸下合理调整侧栏和内容宽度。

#### 会话历史区

-   新建对话入口清晰。
-   会话标题、时间和运行状态具有良好的层级。
-   当前会话状态明显但不过度突出。
-   会话列表支持必要的悬停操作。
-   删除等危险操作有明确反馈。
-   长标题合理截断。
-   有清晰的空状态。
-   运行中的会话在切换会话后仍然能够被识别。
-   保留现有会话选择、删除和运行状态逻辑。

#### 消息区

-   用户消息与助手消息具有清晰但克制的视觉区分。
-   助手消息应以内容可读性为中心，不要给整段回复套厚重的灰色大气泡。
-   Markdown 标题、列表、表格、代码块、引用、链接和图片具有一致排版。
-   代码块支持语言标识、复制和横向滚动。
-   长内容有良好的阅读宽度。
-   消息操作（复制、重试等）按现有真实能力展示。
-   附件有合理的缩略图、文件类型、名称和下载/预览反馈。
-   流式输出期间滚动行为稳定。
-   用户手动向上滚动阅读历史时，不应被强制拉回底部。
-   历史消息恢复后滚动位置正确。
-   保留现有消息锚点或导航能力，若其体验不佳可重新设计，但不能无故删除。

#### Agent 执行过程

对于项目已经支持的能力，设计清晰的过程展示：

-   任务计划或执行阶段。
-   工具调用及其状态。
-   工具输出摘要。
-   运行中、成功、失败、等待审批、已中断等状态。
-   人工审批入口。
-   失败信息与重试入口。
-   最终结果。

不要把所有内部细节无差别地暴露给用户。采用分层展示：默认展示用户真正需要的信息，用户可以展开查看执行细节。

**重要：** 必须基于当前真实消息结构、Run
状态和事件协议实现。不得仅凭前端猜测构造一套与后端不一致的执行时间线。

#### Composer 输入区

-   采用现代 AI 产品的输入框设计。
-   多行输入、Enter 发送、Shift + Enter
    换行等行为与当前产品约定保持一致。
-   附件、模型选择、审批模式等现有入口重新组织。
-   发送、停止生成、禁用和等待状态明确。
-   输入框高度随内容合理增长，设置上限并支持滚动。
-   上传中、上传成功、上传失败有反馈。
-   避免输入框被页面底部遮挡。
-   保留现有模型选择、附件上传和发送逻辑。

#### 产物面板

如果当前项目已有文件预览、报告或其他产物能力，可以将其组织为可展开的右侧面板或独立查看区域。

不得为了模仿 Claude 而凭空增加没有数据来源或业务实现的产物功能。

### 6.2 Dashboard

目标：从传统统计卡片首页升级为真正有用的平台工作台。

-   顶部展示简洁的欢迎信息或平台状态，不使用大面积渐变 Banner。
-   展示真实且有意义的核心指标。
-   快捷入口应服务于常见工作流。

-   数据缺失时展示合理空状态，不能编造指标。

### 6.3 模型配置与供应商管理
